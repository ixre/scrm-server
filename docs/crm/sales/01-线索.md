# 线索（Lead）

销售通过线索管理尚未转化的咨询，领取或分配后记录联系情况、安排下一次联系，再转为客户继续经营。本文按当前路由和实现更新（2026-10-18）。线上渠道当前主要接入客户主档和引流任务，不把“渠道已获客”等同于“所有渠道已自动创建独立销售线索”。

## 入口与访问范围

销售管理 → 线索包含全部可见、本人、线索池。负责人或管理角色可办理本人范围内的有效线索；池中线索可读，需领取后才能预约或写跟进。流失线索先恢复，已转客户的线索继续在客户页面跟进。客户共享不会自动授予线索归属权限。

待办中心的“线索跟进”可直接打开线索详情；详情中的“打开客户”进入客户 360。深链接分别为 `/console/crm/lead?lead_id=<ID>` 和 `/console/crm/customer?customer_id=<ID>`，实际读取仍由后端权限决定。

## 生命周期

`new` 新线索 → 记录跟进或标记联系后为 `contacted` → 转客户为 `qualified`。有效线索可标记 `lost`，填写原因后停止预约；恢复流失线索回到 `contacted`，不自动恢复旧预约。状态通过专用操作改变，普通 Update 不得绕过流程。

当前接口都使用 `crm_lead` 服务，实际路由不是 `crm_lead_ext`：

| 操作 | 行为 |
| --- | --- |
| `Create/Update/Get/Query/Delete` | 基础维护及分页查询；已转化线索不能改回普通线索 |
| `MoveToPool/ReceiveFromPool/ListPool` | 入池清除原归属和预约；领取经过并发状态校验 |
| `Transfer/BatchTransfer` | 校验接收人，转移保留当前预约，由新负责人继续处理 |
| `MarkContacted/MarkLost/Reopen` | 记录状态及操作结果；流失要求原因 |
| `ConvertToCustomer` | 按现有归属和手机号校验复用或新建客户，保留来源及跟进历史，重复请求复用客户 |
| `SetSchedule/History` | 当前预约和跟进历史游标查询 |

导入使用 `BatchImport`，每批最多 1000 行，校验当前有效账号与调用人；旧导入按行返回成功/失败计数。导入失败明细、复杂 CSV 格式及并发去重仍需专项完善，不应把“导入完成”消息视作所有行成功。

## 预约与跟进

模型在 `app/models/crm_sales_models.go`，新增 `next_followup_at/next_action` 为线索当前预约快照，没有物理外键。

在详情点“安排跟进”可独立预约或取消，接口：

```json
{
  "id": "7001",
  "next_followup_at": "2026-10-18 14:00:00",
  "next_action": "演示产品并确认预算"
}
```

提交到 `crm_lead.SetSchedule`。日期按中国时区绑定，也可传 RFC3339；传 null 取消预约。下一步行动最多 512 字。相同时间及行动重复保存不新增历史；预约与操作记录处于同一事务，写历史失败时预约也回滚。池中、流失或已转客户线索禁止直接预约。

`crm_followup.Create` 的 `lead_id/type/content/next_followup_at/next_action` 可在完成本次联系时同时安排下一步。不填写下次时间表示结束当前预约；内容必填。跟进会推进新线索为已联系。未转化线索的预约独立于其关联客户，不覆盖客户原来的预约。

删除跟进会在权限和父线索锁内恢复最新有效历史中的预约；流失、入池或已转化线索不会因此恢复旧预约。独立调整预约也记入跟进历史，用户能够查明时间变化。

## 提醒与交接

每 5 分钟扫描有效租户，对今天内及逾期的线索预约生成站内 `lead_followup` 待办，每批 200 条，按 `(预约时间,ID)` 游标推进，不局限前 500 条。负责人必须有效，线索非池、非流失、非删除且未转客户。

事件按租户、线索、负责人及预约时间去重。已处理/忽略的同一事件不再生成；改期、取消、转移、入池、流失、删除或负责人停用后，旧待处理事件在查询、计数或扫描时失效，历史保留。转移后新负责人获得当前预约的提醒。待办“已处理”只关闭提醒，不会替用户填写跟进。

转客户在同一事务中延续预约：新客户接续线索时间，已有客户保留两者较早时间；原线索预约清空，旧提醒失效，客户提醒按既有机制接续。原历史关联客户，预约及下一步行动仍可追溯。这里只维护一个“下次跟进”，不是支持多项预约的日历；转化后应核对客户当前预约。

这是站内提醒，不等于给客户自动发消息；实际调度延迟仍需部署环境监控。

## 跟进历史

`crm_lead.History` 接收 `{lead_id,cursor,page_size}`，默认 20、最多 100，返回 `items/has_more/next_cursor`，按记录 ID 倒序翻阅。游标绑定租户和线索，每页重新校验读取权限，不执行全历史 COUNT 或 OFFSET。旧 `crm_followup.ListByLead` 超过 1000 条会明确报错，客户端需改用 History，不会静默截断。

详情切换、关闭或卸载后忽略旧响应；读取错误明确显示并可重试，历史不会把接口失败显示成“暂无记录”。写操作在验证时即防重复点击，成功后等待当前详情刷新；旧页面的回调不更新其他线索。

## 升级与验收

迁移 `0024_lead_followup_workflow.sql` 增加两个可空字段和两个租户复合索引，历史预约保持 NULL，不从旧备注推断业务承诺。无新表或物理外键。先备份、恢复副本验证，再执行版本迁移，最后部署 core/dashboard。普通建索引需维护窗口和实际容量评估；旧调度需切换新版后才会生成线索提醒。

隔离 PostgreSQL 专项：`SCRM_TEST_DATABASE_URL=... go test -race ./app/services -run 'TestLeadAppointment|TestLeadHistory|TestLeadImportRequiresActiveActor' -count=1`。验收覆盖并发仅一条提醒、处理后不复活、交接/流失失效、预约写入失败回滚、转客户较早预约接续、独立客户预约不被覆盖、605 条来源扫描、1005 条历史翻阅、游标撤权和导入账号守卫。真实浏览器、渠道账号和千万行混合负载仍需验收。
