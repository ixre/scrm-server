# 回款（Receivables）

本文按当前路由、服务和页面实现更新（2026-10-18）。业务目标是销售能按合同登记、审批和核对收款，经理能处理审批，重复提交不重复入账。

## 入口与权限

商务合同列表及合同详情中的“回款管理”可登记、分页查看、确认和作废回款；“回款计划”维护合同期次，“回款扩展”提供审批操作。客户详情“成交与回款”提供当前可见合同及回款总览，并可进入合同继续办理。

每次请求重新检查有效账号、租户与合同权限；普通销售只能维护本人负责的合同，管理角色按当前权限操作。客户共享或仅客户负责人交接不会赋予另一销售合同权限，合同交接后原负责人不能继续操作。

## 数据与金额口径

模型位于 `app/models/crm_finance_models.go`，通过租户和标量业务 ID 关联，不建立物理外键。

| 对象 | 主要字段与状态 |
| --- | --- |
| 回款计划 | `order_id/customer_id/period_no/plan_date/amount`；状态为 `pending/overdue/received`，合同作废后可为 `cancelled` |
| 实际回款 | `order_id/plan_id/customer_id/amount/received_at/pay_method/pay_account/voucher_no/attachments/remark` |
| 回款状态 | `pending` 待确认、`confirmed` 已确认、`void` 已作废 |
| 审批状态 | `none/pending/approved/rejected`；创建只允许无需审批或提交审批，不允许直接指定通过 |
| 请求幂等 | 可选 `client_request_id`；`request_digest` 仅后端存储，不对外返回或接受提交 |

合同应收 = 合同金额 − 优惠金额。只有未删除、已确认且无需审批或审批通过的回款计入已收；历史空审批状态按无需审批兼容。金额最多两位小数，服务以整数分校验，累计已收不得超过合同应收；关联期次时，该期有效累计回款不得超过计划金额。

计划可以部分收款，部分到账时仍为待回款或逾期，全额到账才为 `received`，没有 `partial/paid` 计划状态。合同 `pay_status` 为 `unpaid/partial/paid`。历史直接登记在合同的余额保留，未关联计划的回款不自动分摊到期次；催款前核对“合同未收”和“计划未核销”，两者不一定相等。

## 操作与接口

所有接口使用 `POST /api/v1/biz/<服务>/<操作>`。前端日期控件的日期字符串由绑定层按中国时区处理，也接受标准 RFC3339 时间。

创建单期使用 `crm_receivables_plan.Create`，字段包括 `order_id`、正整数 `period_no`、`plan_date` 和 `amount`；批量使用 `BatchCreate` 的 `plans` 数组。单次创建最多 1000 期，超出时分批提交。期次不能重复，计划总额不能超过合同应收。修改计划不能低于该期有效已收，有未作废回款时不能删除该计划。

登记使用 `crm_receivables.Create`：

```json
{
  "order_id": "5001",
  "plan_id": "3001",
  "amount": 150000,
  "received_at": "2026-10-18T00:00:00+08:00",
  "pay_method": "transfer",
  "status": "confirmed",
  "approve_status": "none",
  "client_request_id": "5aef7816-1fda-481e-aa52-b2a4f226660c",
  "remark": "客户已打款"
}
```

`customer_id` 可省略，由合同确定；传入时必须匹配。`plan_id` 可省略，传入时必须属于同租户同合同的有效计划。合同作废后禁止新登记。收款方式为 `cash/transfer/wechat/alipay` 等现有业务值。

待确认且无需审批的记录可通过 `Update` 确认；提交经理审批的回款在通过前不计已收。管理角色通过 `Approve`，或通过 `Reject` 提交驳回说明。已审批回款不能直接修改，应作废后重新登记。

作废使用 `crm_receivables.Void`，事务内重新核对合同余额与计划状态；不是退款或银行转账。`Delete` 不允许直接删除已确认回款，需先作废；待处理和已作废记录可按权限删除。单次登记只对应一份合同，跨合同需分别登记。

### 请求重试

新版登记弹窗每次打开生成一个请求键，保留到该弹窗关闭。相同租户、合同、请求键和原始内容的并发或网络重试复用原记录，不重复增加余额或触发新建回款事件；期间记录已经审批或修改时也保留当前状态。同键不同内容明确报冲突，已作废或删除的记录不允许通过重试恢复；事务失败则不占用该键。

网络响应丢失后可在同一弹窗保留原内容重试，或先刷新核对回款列表。关闭后重开、刷新浏览器会生成新键，不能据此判断银行付款是否已登记。旧客户端不传键仍可使用，但没有这项去重保证；该机制不是按凭证号识别重复银行流水。

### 远程选择期次

`crm_receivables_plan.Options` 接收 `{order_id,keyword,cursor,page_size}`，只显示仍有未收金额的有效期次，返回 `items/has_more/next_cursor`。每页默认 50、最大 100，按 ID 倒序游标翻页；`keyword` 为精确匹配的正整数期次。返回金额为十进制文本，含 `amount/remaining_amount/label`。

剩余金额依据同租户、同合同、同计划的有效回款计算，不依赖可能过时的计划状态。游标绑定租户、合同及检索词，每页重新鉴权，作废合同返回空选项。页面支持加载更多及数字搜索，移除了原前 500 期限制；加载失败显示重试入口，切换合同或搜索后忽略旧响应。保存时仍由事务重新校验金额，选择器展示值不是余额预留。

### 列表与汇总

`crm_receivables.List` 支持单号前缀、合同、客户、期次、状态及审批状态；`crm_receivables_plan.List` 支持合同、客户、状态。分页参数为顶层 `{page,page_size}`，默认 20、最多 1000，仍为带总数的传统分页；选择期次应使用 `Options`。

客户维度汇总及明细使用 `crm_customer.BusinessSummary/BusinessRecords`，口径见 [客户画像 360](../customer/08-客户画像360.md)。当前没有独立的 `crm_receivables.Summary` 或 `Query` 路由。

## 提醒与边界

已接入每 5 分钟的站内待办生成：针对有效签约/完成合同，按待收/逾期期次扫描未来 7 天内及逾期计划，分批处理，每个期次独立去重；负责人、计划日期或来源失效后旧待办不再继续提醒。该功能不是给客户自动发送催款消息。新版客户总览和期次选项按有效收款即时核算；旧列表状态筛选仍读取存储状态。

退款、红字冲销、多币种换算、银行流水自动对账以及收款自动创建发票未在本轮实现，需独立产品规则及验收，不能以“作废回款”替代实际退款。

## 多期合同写入优化（2026-10-18）

原先登记、确认、审批或作废回款时，会对每一期单独求和并更新；批量建计划也逐期查重、求和和写入。本轮改为在父合同锁内按当前租户、合同聚合有效回款，统一校验期次金额并批量更新，仅修改状态实际变化的计划。批量建计划按合同一次校验输入及已有期次和总额，每 200 行插入，所有合同、批次处于同一事务，后续批次失败全部回滚；缺少客户的历史合同继续保存 NULL。

专项隔离测试的实测 SQL 调用数：创建 1/605 期分别为 6/10 次；向 1/605 期合同登记一笔关联回款均为 11 次。该数字来自指定测试场景，不是所有入口的固定调用数或生产延迟保证。已覆盖审批/作废、历史余额保留、跨租户/合同隔离、软删除排除、不改无变化期次、数据库状态更新失败回滚和并发总额限制。

复用 0021/0022 的租户/合同/期次及有效回款索引，本轮无新字段、索引或数据库迁移。查询仍需扫描当前合同相关记录并争用该合同写锁；高频大合同、不同租户并发及生产响应时间需按真实负载验证。

## 五轮财务工作台完善（2026-10-18）

1. **有效检索**：审批工作台支持回款单号前缀检索，不区分大小写；`keyword` 去除首尾空白后最多 64 字节，百分号、下划线和反斜杠按字面值匹配。请求有 5 秒执行期限。待审批筛选默认排除已作废记录；显式 `status=void` 仍可查审计历史。其他标签改为按合同筛选，不再展示无效的单号搜索框。
2. **可核对的催款列表**：`ListExpiring/ListOverdue` 按有效关联回款即时计算期次未核销，不依赖历史计划状态。只纳入本人可见、未删除且已签约/完成、仍有合同余额的合同；草稿、作废、已删除和已收满合同不进入催款列表。返回十进制文本 `remaining_amount/order_outstanding_amount`，分别表示期次未核销和合同未收，另含合同名称及编号。未关联期次的回款和历史余额不自动分摊，催款前核对两列。
3. **统一日历**：生成计划日期固定使用中国时区，工作台和回款日期展示也固定中国日历。到期范围为“今天及未来 N 天”的完整日历日期，`days` 默认 7、允许 1 至 365；查询上界为第 N+1 天零时，不漏掉截止日下午记录。`days_until_due` 由后端按中国日历给出，今天为 0、昨天为 -1，不使用客户端小时差取整。
4. **可信加载**：计划和扩展页面明确区分业务错误、网络失败、异常响应与正常空列表，提供错误重试；切换标签、筛选、页码或卸载后，旧响应不更新当前页面。计划搜索仅提交确认后的筛选，并从第 1 页开始；删除导致页码越界时回退到有效页。
5. **安全提交**：新建、编辑和批量计划提交前检查正金额、两位小数、真实日期、有效正整数期次、重复期次及 1000 行上限，并指出错误行。验证开始即防重复点击，提交期间禁止改行、关闭抽屉，失败保留输入；成功等待当前列表刷新，页面已卸载时忽略旧回调。未引入计划创建请求幂等，响应不确定时先核对已有计划，不能自动反复生成。

到期接口使用顶层 `{page,page_size,order_id,days}`（逾期不需 `days`），保留原计划字段并新增上述核销字段。每页沿用默认 20、最多 1000 的传统分页，列表与总数使用只读一致性快照，期限 5 秒。大数据深分页和宽范围总数仍需按实际负载验证。

迁移 `0023_finance_workbench_reads.sql` 仅新增租户/小写回款单号前缀索引，以及不依赖存储状态的租户/计划日期/ID 有效行索引。无数据回填、字段变更或物理外键。先备份、在恢复副本验证，再数据库迁移 → core/dashboard；普通建索引需要维护窗口。

服务专项：`SCRM_TEST_DATABASE_URL=... go test -race ./app/services -run 'TestFinance' -count=1`，覆盖搜索越权与通配符、旧状态、有效审批、跨合同核销、整日日期边界、满额合同排除、负责人交接和闰日。前端请求、响应错误、日期及表单校验由 `npm run test:requests` 覆盖；浏览器完整交互及真实渠道仍需部署验收。
