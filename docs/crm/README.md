## 设计哲学（贯穿所有流程）

1. **渠道无关优先**：所有客户/订单/活动数据通过 `ChannelLink` 解耦，企微 corp_id 降级为维度字段。
2. **多租户 SaaS**：所有 CRM 表 `tenant_id` 顶层分区，业务操作必带 `tenant_id` 隔离。
3. **本地 ID 主键**：CRM 模型主键均为本地 bigint，不依赖企微 external_userid。
4. **异步回调驱动**：企微 / 小红书事件以 webhook 为准同步进 CRM 主档。
5. **闭源核心 + 开放网关**：业务在 `scrm-server`（gRPC :9001），HTTP 在 `gateway` (:9002)，新业务通过 `dispatch` 注册表扩展。

## 调用约定

所有业务接口走 `dispatch` 注册表，HTTP 层在 `gateway`。约定调用形式：

```
POST /api/v1/biz/crm_customer/Create
Headers: Authorization: Bearer <JWT>
Body: {
  "name": "示例客户",
  "mobile": "13800000000"
}
```

返回：

```json
{
  "code": 0,
  "data": { ... }
}
```

完整接口清单参见 `internal/dispatch/crm.go` 的所有 `Reg.Register("crm_*", ...) `。

### 渠道获客闭环补齐（2026-10-17）

**业务目标**：线索进入系统后，销售能明确领取任务、记录处理结果；主管能分派有客户访问权的有效员工、追溯处理过程。客户交接或进入公海后，旧销售不能继续读取或处理任务。

本轮交付边界为“小红书留资 → 客户/渠道身份/互动 → 人工引流任务 → 领取或分配 → 完成/跳过 → 必要时重新打开”。48 小时是当前固定处理期限；超时保留待跟进能力，不自动判定失败。客户已有有效负责人时默认分配，公海客户需先领取客户。这不代表配置页中的通用自动分配规则引擎已实现。

验收依据为 `app/services/crm_channel_task_test.go`：并发重复留资仅一套业务记录；任务写入失败时客户和互动一并回滚；客户合并后渠道身份仍指向主客户；跨租户、停用员工和无客户权限的接收人被拒绝；同一版本并发处理仅一个成功；审计失败回滚任务状态；重复提交相同处理结果不重复记日志；超时后仍可处理；交接立即收回旧负责人权限；分页和迁移重复执行不丢历史记录。

上线后应采集首次响应时长、超时未处理数量、领取到完成耗时、跳过原因分布、重复事件数量与同步失败率。当前只完成业务链路和回归验证，未接入这些产品指标，也未完成真实渠道账号及千万行混合负载验收。下一优先项仍为通用自动分配执行器，其次为受权限约束的客户 360 财务摘要与分页明细。

### 客户历史分页与大企业员工选择（2026-10-17）

本轮修复两项明确的实际使用问题：老客户详情一次读取全部跟进/活动史导致响应持续变大；员工选择只装载前 500 人，后续入职员工无法分配。另修复快速切换客户时旧请求覆盖当前详情的问题。

- `crm_customer.GetDetail` 对跟进、活动参与、非企微互动、转移日志分别返回最近 20 条及 `history_pages`。`crm_customer.History` 以有效时间和 ID 双键倒序分页，默认 20、最多 100 条；不执行全量计数或深层 OFFSET。每次翻页重新检查客户权限，交接后旧游标不能继续读取。
- 客户详情、时间线及跟进弹窗提供“查看更早”入口，计数显示“已加载”，不把当前页数冒充全部历史；详情刷新、关闭或切换时忽略过期响应。
- `crm_user.Options` 仅返回 ID、显示名和状态，按 ID 游标分页，支持姓名/账号搜索及已选 ID 回显。默认只提供有效员工；历史筛选可包含停用员工。客户、线索、商机、合同报价、分配配置及多个扩展页面接入公共远程选择组件，不再受前 500 人限制。专用渠道任务接收人仍保留其客户权限筛选接口。
- 旧跟进/活动 `ListByCustomer` 保留数组结构，最多读取 1001 条用于判断：超过 1000 条明确报错并要求改用 `History`，不会返回不完整数组却声称成功。第三方旧调用方应同步迁移。
