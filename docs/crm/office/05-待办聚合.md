# 待办中心

销售通过 `crm_todo.List` 查看自己的提醒，`crm_todo.Count` 获取待处理计数，`crm_todo.Handle` 将指定提醒标记为 `done` 或 `ignored`。管理员也不能通过该接口处理其他人的个人待办。批量操作全量校验，重复提交相同处理状态幂等；不能改写已失效或其他终态。

## 已实现的核心提醒

- 客户跟进：客户当前预约在今天内或已逾期，客户非公海、非黑名单、非待接收交接，负责人有效。日期使用北京时间，今日区间为当天零点到下一天零点（不含）。
- 线索跟进：未转化、非池、非流失的有效线索当前预约在今天内或逾期，负责人有效；领取前不可预约，转移后提醒归新负责人。
- 回款：已签约/已完成合同下，未来 7 天内或已逾期、尚未收齐的计划；包含 `pending` 和 `overdue`，按每一期分别提醒。
- 服务端 `CrmGenerateReminders` 每 5 分钟扫描有效租户，每页 100 个租户、每批 200 个来源记录。每个租户每类生成有 30 秒执行预算，失败记录日志，后续扫描通过事件去重继续推进。单实例调度不重叠，多实例由数据库唯一键确保去重。

“已处理”仅关闭提醒，不代表客户已经跟进或款项实际到账。销售需要在线索或客户中登记跟进、在合同中登记真实回款。完整审批、工单、站外通知、主管升级通知尚未统一纳入本提醒机制，不能仅根据类型枚举判断已实现。

## 生命周期与数据结构

`CrmTodo` 保留 `tenant_id`、`user_id`、`type`、标题、内容、`ref_type/ref_id`、`due_at/status`，新增：

| 字段 | 用途 |
| --- | --- |
| `source_id` | 真实提醒来源，客户跟进为客户 ID，线索跟进为线索 ID，回款为计划 ID；合同导航仍使用 ref_id |
| `event_key` | 来源、负责人、预约时间组成的事件去重键；租户内唯一，包含已处理历史，接口不返回 |
| `handled_at` | 人工处理或自动失效的时间 |

状态：`pending` 待处理、`done` 已处理、`ignored` 已忽略、`cancelled` 已失效。改期、交接、入海、拉黑、来源删除、合同取消、计划已回款时，旧 pending 提醒自动失效且保留历史。查询列表和数量前会重新核对来源，避免等待下一次调度。新负责人或新预约产生新事件；同一来源恢复有效时，可恢复尚未人工处理的 cancelled 事件。已处理/忽略事件不复活。

数据依赖采用逻辑 ID 和租户前缀复合索引，没有增加物理外键。来源扫描采用 `(到期时间, ID)` 游标，已存在事件通过数据库 `NOT EXISTS` 排除；避免固定前 500 条饥饿、逐条查合同和计数、全租户 ID 拉入内存。

## 升级

迁移 `0016_actionable_reminders.sql` 增加三列、唯一事件索引和六个查询索引。旧 pending 跟进/回款提醒缺乏事件与期次信息，会保留为 cancelled，由新调度根据当前业务来源重新生成；旧 done/ignored 历史保留，无法精确识别的旧已处理回款事件可能在升级后产生一次当前有效提醒。不会自动修改客户、合同、回款金额或回款状态。

先备份，停旧调度，执行 `go run ./cmd/migrate -schema-only`，再启动新版本服务。迁移创建索引需要维护窗口，大表应先在数据副本测量耗时。单次扫描的预算与索引不等同于千万行、多实例下的容量认证；需要观察每类任务执行耗时、超时和积压。

线索预约闭环由迁移 0024 补齐，流程见 [线索](../sales/01-线索.md)。待办提供线索/客户办理链接，日期按中国时区展示，列表及统计错误明确显示并支持重试。提醒生成仍由 5 分钟调度触发，保存预约后不承诺立即出现；需要部署并监控调度。
